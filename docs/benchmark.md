# Comparative benchmark preparation

**Status: protocol and offline measurement analysis only. No comparative benchmark has been performed by this document or analyzer. There are no measured results here, and no claim that Tandem is superior.** Running an independent review, testing compatibility, or observing one live case is not a four-arm benchmark. This preparation neither schedules model requests nor commits anyone to paid runs. Execution requires separate dataset, privacy, resource, and spending approval.

## Question and four arms

Compare task quality, false positives, regressions, completion, total process latency, human effort, and **coordinator-inclusive** consumption. Do not reduce the question to whether an extra agent finds something.

| Record `arm` | Frozen intervention |
| --- | --- |
| `one_agent` | One coordinator solves the task and supplies the final artifact. No explicit second review pass or peer. Ordinary reasoning and checking are allowed under the common tool policy. |
| `self_review` | The same coordinator first produces its answer, then receives a fixed self-review instruction and revises once. No separate agent or fresh peer context. Count both passes and finalization. |
| `naive_handoff` | Coordinator produces a candidate; a fresh peer receives that candidate plus the same task inputs, reviews once, and returns findings; coordinator integrates once. The peer sees the author's proposal from the start. |
| `tandem_independent` | Coordinator produces its candidate; a fresh peer first reasons from the frozen task/snapshot without the author's answer, then compares the candidate to that independent answer on the same snapshot/conversation. Coordinator integrates once. Use the compact review workflow for suitable review tasks; for other tasks freeze the equivalent independent-first think/compare instructions. Record actual tool/run/task IDs. |

Freeze the exact prompts, permissions, tool allowlist, answer format, integration rules, context visibility, and per-arm stopping policy. Never silently allow one arm additional internet access, source files, retries, author edits, or oracle answers. All four use the same pinned coordinator model; both two-agent arms use the same pinned peer model. Model selection is a treatment-independent decision, not something tuned after seeing results. Single-agent arms still declare the experiment's peer model in `versions`; their peer usage is explicitly inapplicable.

The comparison is of these complete workflows, not an isolated claim about a particular tool. Do not force a review-only API to implement features or apply results automatically. Save the final coordinator answer and final diff, not merely the OMP peer's output.

## Dataset freeze and approval

1. Select **20–30 tasks before any scored run**. A recommended balanced design is 24 tasks, six per stratum. If choosing another size, allocate 5–8 tasks to each stratum and justify any imbalance in advance:
   - **Bugs:** observable incorrect behavior with a minimal reproduction, including boundary/state cases; mix local and cross-module causes.
   - **Small features:** bounded acceptance criteria, including backward compatibility and negative cases; no open-ended product builds.
   - **Architectural ambiguity:** incomplete or competing plausible designs, explicit constraints/trade-offs, and a rubric that rewards appropriate uncertainty/questions instead of verbosity or one preferred implementation.
   - **Reviews:** frozen candidate changes containing adjudicable issues, including clean changes/decoys to measure false positives. Include both worktree and staged inputs where relevant.
2. Balance language, repository, task size, difficulty, and expected context across arms by pairing the *same* tasks, not by choosing four different task sets. Include multiple repositories; disclose task provenance, selection/exclusion criteria, prior model exposure, and possible training contamination. Avoid selecting only tasks where a preliminary Tandem run helped. Pilot on separate unscored tasks; exclude pilots from the frozen set.
3. Make an immutable input bundle for each task: repository identity, base commit and tree, task text, selected diff, index/worktree contents as appropriate, unchanged context, dependency lockfiles, permitted fixtures, tool settings, and any standardized clarification script. Hash exact bytes. A staged review's context comes from the index, not the live working tree. Do not silently expand a captured snapshot when an agent asks a question. Return the same preapproved clarification to every arm; if genuinely new information is necessary, freeze a new input version and rerun *all* arms in a newly approved block.
4. Prepare hidden acceptance checks and the grading rubric independently of arm outputs. Archive reference diagnoses and review issue definitions, including severity and what makes a finding actionable. Keep these inaccessible to agents. Hash rubric and dataset bundles before execution.
5. Freeze exact versions: Python patch version, Tandem version **and source commit**, OMP binary version and digest, OMP RPC SDK commit, provider/model snapshot IDs, inference settings, OS/hardware/container identity, dependency locks, resource limits, tool versions, networking, and pricing snapshot. The compatibility target for this release is OMP `18.1.13` and RPC SDK `daf07999c2fee9b22edc7bf8fea1fb6272e0df5e`; record what was actually used rather than inferring that a target was exercised. A moving model alias must be disclosed; inability to identify a provider snapshot limits reproducibility.
6. Obtain written approval of task set, grading, budgets, permitted execution environment, data handling, and stopping rules. Archive the approval with its digest. Keep secrets/private source outside public artifacts; publish authorized redactions with a manifest and explain what cannot be independently verified. Approval of this protocol alone is not permission for paid execution.

Use SHA-256 lowercase hexadecimal digests. For directories/bundles, hash an archived manifest with sorted relative paths and each file's SHA-256 (no timestamps or absolute paths), then hash that manifest's exact UTF-8 bytes. Archive those exact bytes; do not rely on reserializing JSON identically. `input_digest` covers one task's input manifest; `dataset_digest` covers the ordered task/input manifest and hidden-check references; `protocol_digest` covers the frozen protocol; `rubric_digest` covers the grading rubric; each arm configuration has its own digest. `experiment_digest` covers a separate experiment manifest containing these digests, versions, schedule/budgets, pricing, and resource policy. The separate manifest does **not** contain its own hash or the final plan/approval hash, avoiding circular hashes. `versions.environment_digest` points to the environment manifest. The analyzer checks declared identities for consistency; it does not fetch artifacts or establish that their bytes, approval, or measurements are authentic.

## Paired runs and independent budget regimes

Freeze a plan with all tasks, repetition count, both regimes, and a nonnegative randomization seed. Prefer at least three repetitions per task/arm/regime when approved; one repetition is allowed but has very limited precision. A block is `(task_id, repetition, regime)`, with all four arms. Reset to the same frozen input and clean sessions before each arm. No answer sharing across arms or repetitions; disable cross-run memory and disclose cache policy. No tuning prompts or budgets after results arrive.

Run blocks in lexicographic `task_id`, then ascending repetition, then `natural`, `equal_compute` order. Within each block, rank the four arms by ascending SHA-256 digest of the UTF-8 JSON array `[randomization_seed, task_id, repetition, regime, arm]`, serialized with `ensure_ascii=True` and separators `(',', ':')` (no whitespace). `scripts.benchmark.arm_order` implements this permutation. Record the resulting one-based `order`. This gives reproducible randomized arm order without depending on a PRNG version. Execute benchmark arms sequentially on the same reserved resources; concurrency *inside* an arm remains allowed and is counted honestly. Interleave blocks rather than running every baseline first. Archive actual scheduling disruptions and provider incidents.

Analyze the following **separately**; never pool them into one leaderboard:

- **Natural:** common whole-process wall limit; each workflow uses its frozen natural number of passes and stopping rules. `compute_limit_usd` is `null` because no per-run equal-compute cap applies. A separately approved overall safety/spending ceiling still applies; if it stops the study, retain all attempted records and show unattempted slots as missing. Report real cost instead of implying the extra review was free.
- **Equal compute:** the same total USD inference cap and wall limit for all four arms, counting coordinator **plus** peer and all retries/tool-related model calls. Freeze pricing and cap enforcement/reservation (including in-flight maximum charge), and the allocation policy across passes before execution. Any per-arm allocation is in the frozen arm configuration; the shared budget `policy_digest` covers the complete policy. Do not give the coordinator a full cap and then add a separate peer allowance. This regime measures equal billed compute at the frozen prices, not equal FLOPs. Do not relabel equal peer tokens as equal total compute. If the cap cannot be enforced/observed, mark compliance `unknown`, not `within`.

Record overruns as `exceeded`, keep their outcomes in arm summaries, and exclude them from within-budget paired estimates. Unknown compliance is also excluded from paired estimates. Report exclusion counts prominently: this compliant subset can be selected and must not be represented as an intention-to-treat causal result. Pre-register an intention-to-treat sensitivity analysis over all attempted outputs if making a comparative claim; this CLI deliberately only supplies descriptive arm summaries and clearly labeled within-budget pair differences. Changing a policy, limit, version, input, or configuration requires a new experiment/plan; never quietly join incompatible observations. Natural and equal-compute records may share task IDs but are never paired to one another.

## Timing and complete accounting

Start a **single monotonic clock before task-specific process/workspace startup** and stop after final coordinator output and artifact capture, including shutdown required by the run. `wall_time_seconds` is that elapsed interval. It includes coordinator reasoning, peer startup/execution, independent/comparison stages, tool runs, retries, questions and human waiting, final integration, and failures/timeouts. Never sum concurrent stage durations, average child durations, or substitute OMP task duration for the whole process. Preserve clock observations in the provenance artifacts. UTC `started_at`/`finished_at` aid audit; monotonic elapsed time is authoritative when wall clocks move. Shared one-time provisioning and post-run blind grading are outside this task latency; disclose their wall/person time separately in the study report. Do not label task latency as total study duration.

`human_seconds` counts active person-seconds attributable to a task: task-specific preparation, interventions, recovery, and grading/adjudication. Allocate shared preparation by a frozen policy and keep category-level evidence; simultaneous work by two people is two people's effort, not process latency. A measured zero is allowed; untracked time is `missing` and partially tracked time is `partial`. An agent waiting on a human contributes to wall time even when the human is not actively working.

For each role (`coordinator`, `peer`), collect all billed model turns from provider receipts, raw usage logs, or a frozen pricing calculation with explicit provenance. Include self-review, final integration, failed/aborted requests that were billed, comparison turns, automatic retries, and model-backed helper calls. Attribute a call once, by the frozen role ownership rule; do not double count cached/input/total counters or a peer call visible in both coordinator and OMP logs. Token conventions: input counts include cached input once; output counts include reasoning tokens once when the provider supplies them. Keep provider-specific subdivisions, cache charges, request IDs and price calculations in the raw evidence. If those totals cannot be recovered, mark the affected token metric partial/missing. Costs are actual USD charges or recomputed charges at the frozen public price schedule; disclose discounts, credits, estimates, and non-model infrastructure charges separately. Do not mix price bases across arms.

Each `cost_usd`, `input_tokens`, and `output_tokens` metric has `status` and `value`:

| Status | Value and meaning |
| --- | --- |
| `complete` | Nonnegative measured value, including a genuinely observed zero. All applicable calls are accounted for. |
| `partial` | Nonnegative **known lower bound** from a strict subset of calls; explain what is absent. Not an estimate of the total. |
| `missing` | `null`; applicable measurement unavailable. |
| `not_applicable` | `null`; only peer metrics in the two single-agent arms. Never use this for an uninstrumented coordinator or a two-agent peer that failed before returning usage. |

Every measured/partial role needs evidence references and a note. A peer that never launched in a two-agent attempt may have complete zero usage **only with evidence that no billable peer request occurred**; it is not inapplicable. OMP exposes OMP-side usage, not the external coordinator's total cost. If coordinator usage is unavailable, total cost remains partial/missing even when OMP usage is complete. Unknown is never zero. Whole-process totals are complete only when all applicable role measurements are complete; absent peers in one-agent arms are excluded, not fabricated as zero-valued measurements. No separate dollars-per-score claim is defensible when total cost coverage is inadequate.

## Blind grading, failures, and disagreement

Strip arm labels, tool names, model IDs, transcripts revealing the intervention, and timing/cost metadata from grading packages. Preserve the substance of the final answer/diff and a consistent format. Randomize opaque output IDs independently of execution order and keep the key with a non-grading custodian. Have two independent graders apply the frozen rubric before discussion; save their original grades and evidence. An adjudicator resolves disagreements blind. Disclosure is required if style reveals an arm or blinding is broken; do not assert `blind: true` for a knowingly unblinded grade (retain the raw evidence, set `judgment: null`, and explain the limitation).

Freeze the rubric before running: quality on 0–100 from task-specific correctness/acceptance checks, completeness, compatibility and justified reasoning, with explicit scoring anchors and weights per stratum. For review tasks, score severity-weighted true issues and actionable evidence, while counting unsupported/incorrect actionable claims as **false positives**; do not reward finding count alone. Independently test outputs for **new regressions**, including behavior outside the task's positive checks. Deduplicate multiple reports of the same root issue by a predeclared rule. Report false-positive counts alongside true-issue coverage in the grading evidence; a clean review is not a failure to be productive. Do not equate stylistic preferences with defects.

Grade the final artifact of every attempted run when possible, including partial output. `outcome.status` is one of `completed`, `unfinished`, `refused`, `timeout`, `failed`, `cancelled`; it is operational status, **not correctness**. A confidently wrong answer can be operationally completed and receive a poor grade. Do not discard refusals, timeouts, unfinished work, provider failures, or interrupted runs as outliers. Preserve their reason, artifacts, elapsed time, and consumed usage. Unattempted slots have no invented measurement row; the plan makes them visible. Technical replacement attempts are not silently substituted: freeze the retry policy, charge all retries within the original attempt, or retain a separate newly approved repetition/experiment and disclose the deviation.

`judgment.disagreements` counts rubric items on which initial graders disagreed; retain pre-adjudication differences. `adjudication` is `agreed`, `resolved`, or `unresolved`. Provisional unresolved grades remain in the raw record but are **withheld from quality/false-positive/regression aggregates and paired deltas**; disagreement counts still appear. If grading has not occurred, `judgment` is `null`, not a zero score. `outcome.peer_disagreements` separately counts distinct substantive author/peer conflicts under a frozen coding rule; `null` means unknown (or inapplicable without a peer), not agreement. Preserve whether conflicts were resolved, ignored, or still open in outcome evidence. Never present model agreement as ground-truth correctness.

## Collect files and run the offline analyzer

The repository supplies:

- `config/benchmark-result.schema.json`: Draft 2020-12 schema for **actual measurement records** (root), plus the frozen plan at `#/$defs/plan`.
- `scripts/benchmark.py`: stdlib plus the already-declared development dependency `jsonschema`; reads local JSON/JSONL, validates, and emits JSON summaries. No models, network requests, benchmark execution, or artifact fetching.
- `tests/test_benchmark.py`: synthetic regression fixtures only, not measured data or benchmark evidence.

Create an approved `benchmark-plan.json` using the plan schema. Required fields are `schema_version: 1`, `kind: "benchmark_plan"`, an experiment ID, the five identity digests (`protocol_digest`, `dataset_digest`, `experiment_digest`, `rubric_digest`, and `versions.environment_digest`), full `versions`, four `arm_config_digests`, 20–30 `tasks` with `task_id`/`stratum`/`input_digest`, `repetitions`, exactly two `budgets` (one per regime), `randomization_seed`, and the `approval` artifact. A budget contains `regime`, `policy_digest`, positive `wall_limit_seconds`, and `compute_limit_usd` (`null` for natural, positive for equal compute). An artifact contains `uri` and `sha256`; local paths or durable authorized archive locations are acceptable.

For each actual attempt, append **one JSON object per line** to `measurements.jsonl`. Collect, do not prefill, the following:

| Record section | Source |
| --- | --- |
| `schema_version: 1`, `kind: "measurement"`, unique `record_id` | Collector metadata; stable unique ID for the attempted arm slot. |
| `experiment_id`, `protocol_digest`, `dataset_digest`, `experiment_digest`, `versions` | Exact approved plan values. |
| `task_id`, `stratum`, `input_digest`, `arm`, `arm_config_digest`, `repetition`, `order`, `budget` | Frozen task and randomized schedule; repetition/order are one-based. |
| `provenance` | Collector identity/version; timezone-qualified UTC start/finish; `clock: "monotonic_whole_process"`; nonempty artifact list (raw clocks, transcripts, final output/diff, request/run IDs); nonempty notes explaining collection limitations. |
| `outcome` | Observed operational status/reason, `budget_compliance` (`within`/`exceeded`/`unknown`), and peer disagreement count or `null`. |
| `wall_time_seconds`, `human_seconds` | Whole-process elapsed observation and human-effort metric, not summed child time. |
| `usage.coordinator`, `usage.peer` | Each has all three metrics, evidence artifact array, and a note; unavailable evidence uses the explicit missing statuses. |
| `judgment` | `null` until blinded grading; otherwise `blind: true`, frozen `rubric_digest`, evidence artifact, score, false-positive/regression/disagreement counts, and adjudication state. |

These are field instructions, **not a sample result**. No template containing plausible-looking timings, costs, scores, or results is shipped. Obtain actual measurements before emitting measurement records. Use the JSON schema as the machine-readable shape; it rejects unknown fields. Keep raw artifacts immutable. If enriching a record with grading or late provider receipts, produce a versioned replacement JSONL with exactly one current row per original `record_id`, retain the old file and an audit changelog, and never append a duplicate row as though it were another run.

From the repository root, with approved plan and collected records in place, the single analysis command is:

```sh
uv run --group dev python scripts/benchmark.py --plan benchmark-plan.json measurements.jsonl
```

JSON summary goes to stdout; errors go to stderr with exit code 2 and no partial report. An empty JSONL is valid for checking a plan and reports all slots absent, **not a completed benchmark**. The CLI rejects duplicate record IDs/arm slots, duplicate JSON object keys, malformed/schema-invalid records, non-finite numbers (including overflow such as `1e999`), unplanned tasks/repetitions, changed inputs/versions/configurations, incompatible budget policies/limits, incorrect randomized order, invalid role applicability, and unsupported equal-compute compliance claims. Separate files/plans are required for separate experiments.

Output contains per-arm **and per-stratum**, per-regime outcomes, budget/adjudication counts, metric coverage, and all six pairwise comparisons. `missing_slots` exposes even entire unattempted task blocks. For each metric, `complete_sum` and `complete_mean` use only complete observations; they are `null` if there are none. `known_lower_bound_sum` includes complete and partial observed values, never substitutes for a full sum, and is `null` if nothing was observed. `coverage` separates complete, partial, missing, and inapplicable values, while `absent_records` counts unattempted/unreported slots. A sum of complete records is **not** the complete experiment cost when coverage is incomplete.

Pair metrics report `mean_right_minus_left` only for same-task, same-repetition, same-regime compatible records with both budgets marked within and both metric values complete. Each metric reports its own `complete_pairs`/`unavailable_pairs`; there is no universal denominator. Positive quality deltas favor the right arm; positive cost/time/error-count deltas do not. Complete records from different tasks are never substituted for a missing partner. Raw arm summaries retain failures/overruns instead of hiding them. The CLI does not calculate significance, prove causality, verify provenance bytes, infer missing provider charges, or declare a winner.

## Reporting and interpretation before any claim

Publish the approved freeze manifest, collection code/version, randomized schedule, authorized raw evidence, full records and analyzer output, task exclusions/deviations, status distributions, blinded grading/adjudication evidence, human effort categories, and coverage for **both** coordinator and peer. Include all four arms and both regimes, or explicitly state the uncollected cells and that comparison is incomplete. Disclose infrastructure/pricing changes and missing/partial measurements. Never merge an OMP-only cost observation into a coordinator-inclusive table as though they were the same metric.

Pre-register primary metrics and direction before execution. Present paired task-level effects, per-stratum distributions, and uncertainty rather than ranking by one aggregate. If adding intervals, resample **task blocks**, keeping all arms/repetitions together (not independent repetitions or individual model calls); record the method, seed, and interval level. A 20–30-task study is exploratory and may be underpowered, especially per stratum. Correct for multiple comparisons or label them exploratory; include a sensitivity analysis for missingness, unresolved grades, and noncompliant budgets. This analyzer supplies descriptive summaries, not those inferential analyses. No superiority claim is justified by the preparation, a tiny selected example, extra findings without false-positive checks, or unavailable total cost.
