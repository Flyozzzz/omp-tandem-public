## 0. Решение в одном абзаце

Прошлая совместная разработка завершена и дала полезный результат. Не начинать её заново. Следующая итерация должна закрыть оставшиеся границы применимости независимого ревью, уменьшить объём служебного контекста, сделать восстановление ручной работы серверным и понятным, согласовать контракт финального отчёта с реальной историей проверок. **Не включать production helpers и не заменять независимую приёмку автоматическим одобрением ради скорости.**

Документ сам по себе не разрешает новые платные вызовы, автономный daemon, расширение shell-доступа, push/tag/publish/apply. Работать в пределах отдельно полученных полномочий.

## 2. Основания нового ТЗ: что наблюдалось, что измерено, что требует регрессии

Обозначения:

- **[RUN]** — составитель выполнил локальный изолированный сценарий без провайдера и без изменения живого проекта/карточки.
- **[RECORD]** — факт сохранённой истории; проверки принадлежат указанному участнику.
- **[CODE]** — прослеженный путь в исходниках `b153e85`; факт использования этого пути в завершённой работе не утверждается.
- **[DESIGN]** — выбранное требование следующей итерации, а не найденный инцидент.

### E1. Большое представление карточки [RUN]

На одноразовой копии завершённой БД вызван текущий `WorkStore.perform(get)` версии 3.5.0. JSON сериализован с `ensure_ascii=False`, без форматирующих пробелов:

- весь view: **193 653 байта UTF-8 / 191 797 символов**;
- `markdown`: 33 432 байта;
- `plan`: 21 597 байт;
- `steps` с развёрнутыми attempts и evidence: 131 658 байт.

Это измерение domain view **до MCP-обёртки**, не точное количество токенов запроса модели. `_view()` разворачивает попытки, включает полный план/результаты и добавляет Markdown того же состояния; обычный `get` не является компактным progress view.

### E2. Опубликованная schema и runtime расходятся [RUN]

`TaskOutcome.model_json_schema()` — именно схема, передаваемая в host tool. Проверка стандартным JSON Schema validator и Pydantic дала:

| Вход | JSON Schema | Runtime |
|---|---|---|
| `outcome=success` и check с `result=failed` | Принимает | Отклоняет |
| `outcome=blocked` без blockers | Принимает | Отклоняет |
| Короткий корректный success с answer/summary | Принимает | Принимает |

Причина — межполевые правила `TaskOutcome.validate_outcome`, не выраженные в обычной generated schema. Это более точное основание, чем повторять старое общее замечание «tandem_finish сломан».

### E3. Финальный успех и история проверок неудобно совмещаются [RECORD]

B2 уже принят, но native task завершён `partial`, чтобы не скрыть первый failed wake-check после успешного повторного прогона. В интеграции текущие required passes оставлены в structured checks, а исторические failed/unrun — в прозе и артефактах. Нужна структура для истории и применимости, а не превращение failed в passed или разрешение любого success.

### E4. Восстановление ручного claim требовало отдельного модельного хода [RECORD + CODE]

Task `8b545c8d-ae9b-4636-b4b0-542cd3994c9e` завершился `cyber_policy` после публикации finding `cd702e97-121c-4d6d-a4bf-750ec9f86438`. Следующий узкий task `36016be8-c0a6-4216-9587-6eae01193c49` восстановил прежний claim точным повтором старого запроса и записал reject без повторных тестов.

`NativeWorker` создаёт task-local `claims={}`; `Bridge` имеет отдельный session-local cache. Сервер уже умеет вернуть действующий claim по exact receipt — отсутствует удобная долговечная привязка к разрешённому продолжению.

**Не заявлять потерю артефактов как открытый баг:** `TaskResults.view()` уже возвращает `provisional_artifacts`, даже если `result_artifacts=[]`. Сохранить и использовать этот путь, не создавать его второй раз.

### E5. Старый shell waiver применяется к новому плану [RUN]

В отдельном Git-репозитории и отдельной БД выполнен store-level сценарий:

1. План 1, shell grant, готовая fixture submission.
2. Review reservation правильно блокируется до operator decision.
3. Оператор снимает server-minted blocker для исходных критериев.
4. `propose` меняет acceptance того же `step_id`; оба снова agree; создан новый shell grant.
5. После новой fixture submission review успешно резервируется **без нового решения**.

Наблюдалось: `plan_revision=2`, новый grant, `waiver.origin.plan_revision=1`, unresolved policy blockers = 0, `allow_shell=false` у review.

Это **не выдача reviewer права на shell**. Это перенос старого решения об отказе от проверок на новые требования. Старые исправления подделки marker/actor остаются правильными; здесь другая граница — применимость настоящего operator decision.

### E6. Ask/reply остаётся отдельным каналом reviewer input [CODE]

`NativeWorker.worker_tools()` оставляет `tandem_ask` essential и для managed independent reviewer. `tandem_reply` принимает свободный текст; `TaskInteraction.ask()` возвращает этот текст worker без проверки trusted review stage и без изменения exposure provenance.

Следовательно, можно прислать авторское объяснение обычным ответом на уточнение до report/compare, сохранив label independent-first. Путь прослежен статически; **sentinel-эксперимент с модельным входом не выполнялся, использование канала в завершённой работе не установлено**. В реализации первым шагом нужен локальный regression с настоящими callbacks, без платной модели.

### E7. Безопасный unchanged context не подключён к shared review [CODE]

`ReviewStore` уже поддерживает `context_paths`, но `_pin_snapshot_request()` shared adapter не передаёт их; `WorkStep` не объявляет review read-context. По умолчанию snapshot содержит diff-selected paths. Snapshot-only reviewer не может дочитать неизменённый caller/test из того же commit. Отказ reader корректен; улучшать нужно комплектацию снимка, а не возвращать произвольный filesystem read.

### E8. Неопределённость wake-ack сохранена честно, но не устранена [RECORD + CODE]

Инцидент: после `get` оставался pending wake; повторные прогоны прошли. Исходное interleaving не трассировалось. `acknowledge_work` документирован как best-effort, использует `busy_timeout=0`, при BUSY/LOCKED возвращает 0. Немедленное обязательное исчезновение hint сильнее этого контракта. **SQLite contention — не доказанная причина первоначального падения.**

### E9. Статус выдаёт отсутствие apply за известный факт [RUN + CODE]

Текущий исходный HEAD и принятый результат равны `b153e85`, тег v3.5.0 опубликован. Но view по-прежнему говорит: `All steps independently accepted; output is not merged into the user's branch.`

Сервер не проверяет текущий Git и не хранит в карточке факт внешнего переноса. Следовательно, честное состояние здесь — «приёмка завершена, применение этой карточкой не установлено», а не безусловное «не применено».

## 3. Цели и неизменяемые ограничения

### Цели

1. Решение оператора действует только в явно обозначенном контексте; новый план не наследует отказ от обязательных проверок молча.
2. Все каналы declared independent-first review подчиняются одной policy, включая clarification и recovery.
3. Клиент получает небольшой текущий статус и точные допустимые действия, а не многократную копию всего договора и evidence.
4. Завершение, verdict, история проверок, версия рабочего сервера и применение результата представлены раздельно и правдиво.
5. Сбой сохраняет уже сделанное; законный участник может закрыть или явно продолжить тот же claim без восстановления секретов из prompt.
6. Проверки связаны с конкретными байтами и окружением; устранена необходимость повторять неизменный author full suite только из-за времени записи commit.

### Сохранить

- Exact plan agreement, CAS, стабильные operation receipts, разные исполнитель и reviewer.
- Immutable submission/snapshot/report, отдельные report → optional compare → verdict.
- Blocker origin/history, operator-only resolution там, где требуется operator.
- Неизвестные расходы, recovery и неподтверждённая остановка запрещают автоматическое переисполнение.
- Прежние приёмки относятся к прежним байтам. Миграция не превращает legacy review в технически независимое.
- No-shell означает отсутствие произвольного shell; ограничения инструментов не объявлять ОС-песочницей.
- Новые чтения и аналитические отчёты не запускают модели, не выдают разрешения и не изменяют рабочий план.

## 4. SAFE — применимость решений и полнота review boundary

**Приоритет: P0 для scope waiver; P1 для clarification и context. Одна согласованная граница, не три независимых обходных решения.**

### SAFE-1. Привязать no-shell waiver к контексту решения

Сохранить server-minted policy marker и проверку operator provenance. Дополнительно закрепить применимость waiver.

Выбранный default: решение относится к точным `work_id`, `step_id`, `plan_revision`, review submission/snapshot и текущему authorization identity. Причина, evidence, неисполненные проверки и время решения сохраняются. Точный повтор review того же контекста может использовать то же решение; новая версия плана, новый submission или новый grant требуют нового явного решения применимости.

- Старый waiver остаётся историей, не переписывается и не удаляется.
- Новый context не ищет разрешение по совпадающему тексту, одному step_id или факту прежнего `resolved_by=operator`.
- Если старые данные не позволяют установить scope, решение не повышать до глобального: требуется operator review применимости.
- No-shell grant не означает, что все текстовые acceptance checks автоматически выполнены. Неисполненные обязательные проверки остаются видимыми; нельзя «понять из текста», что оператор от них отказался.
- Blocker создаётся до запуска reviewer и расходования launch slot. Не включать shell как способ решить проблему.

**Приёмка:** исходный сценарий E5 перестаёт пропускать review в новом контексте; положительный exact-context повтор остаётся идемпотентным. Сохранить отрицательные сценарии participant same-text blocker и operator record без server marker. Проверить новую submission без смены plan, новый grant и legacy waiver без scope отдельно.

### SAFE-2. Закрыть неявное author disclosure через clarification

До завершения независимой оценки managed independent-first reviewer не должен получать произвольный свободный текст координатора с сохранением обещания withheld author material.

Выбранный путь: **не классифицировать смысл текста моделью**. Если нужны новые требования или дополнительные source paths, вернуть явное `clarification_requires_new_snapshot`/context request, сохранить причину, завершить соответствующую стадию как partial/blocked и пройти явное создание нового snapshot/попытки. Новые данные не подмешиваются в старый immutable independent report. Не отправлять запрещённый ответ в модель, а потом лишь менять label.

- Проверять trusted attempt/stage в общей точке обработки вопроса и ответа, не только наличие/отсутствие tool в списке.
- Ошибка должна объяснять безопасный следующий шаг; отсутствие контекста не оставлять бессрочным ожиданием.
- После разрешённого compare действует обычная политика уточнений этого режима. Обычные неревью-задачи не теряют ask/reply.
- Manual/legacy с уже раскрытым материалом маркируется как disclosed/attested, а не «исправляется» задним числом.
- Проверить и явно описать отношение к низкоуровневому review-run: одинаковая заявленная гарантия не должна иметь скрытый второй смысл.

**Приёмка:** через реальные зарегистрированные callbacks воспроизвести ask → reply с author sentinel до report. Sentinel не достигает model-boundary input независимой стадии. Late/duplicate reply, отмена и timeout не открывают старую стадию. Допустимые вопросы обычной задачи продолжают работать. Отключение одного tool без проверки прямого callback не считается полным исправлением.

### SAFE-3. Добавить точный review read-context без расширения write ownership

Добавить к шагу декларацию `review_context_paths`: точные относительные пути неизменённых callers/tests/dependencies. Использовать существующий `ReviewRequest.context_paths`, а не второй механизм чтения.

- Декларация входит в версию согласованного плана и snapshot identity.
- Содержимое берётся из того же pinned commit, не из текущего worktree.
- В manifest различать changed source и unchanged context; хранить fingerprints.
- Read-context не даёт права записи и не расширяет `owned_files`.
- Недостающий путь означает конкретный partial/blocked с причиной. Расширение — новый immutable snapshot/attempt; старый report не становится оценкой новых данных.
- Не разрешать обходы через absolute paths, `..`, `.git`, state/config/log URI, symlink dereference или скрытый live fallback. Сохранить существующие размерные пределы.

**Приёмка:** reviewer читает объявленный неизменённый caller из правильного commit; не объявленный путь отклонён; изменение live caller после capture не меняет ответ reader; bytes нового context не наследуют старую приёмку.

## 5. REPORT — один исполнимый контракт и неизменяемая история проверок

**Приоритет: P1.**

### REPORT-1. Согласовать schema, runtime и tool instructions

Выразить outcome-зависимые формы TaskOutcome в schema, которую реально поддерживает host transport. Не объявлять успех, если просто перестал падать декодер.

- Сначала проверить поддерживаемое подмножество JSON Schema фактического OMP/SDK. Не навязывать неподдерживаемый conditional/union.
- Generated schema, runtime validation и примеры строятся из одной модели правил; не поддерживать независимые списки обязательных полей в трёх местах.
- Success с текущими обязательными failed/not_run или blockers остаётся недопустимым. Blocked без содержательной причины остаётся недопустимым.
- Ошибка указывает код, invalid fields и допустимое исправление, но не меняет outcome за исполнителя.
- Короткий ответ разрешён в `answer`; summary отдельно. Артефакт не обязателен только ради финального текста.
- Отсутствие `tandem_finish` не превращается в success. Точный повтор финального отчёта идемпотентен, отличающийся второй отчёт отвергается.

**Приёмка:** E2 даёт одинаковое решение schema и runtime для всех трёх случаев; проверить фактическую регистрацию host tool, а не только исходный docstring. Не снимать защиту ради совпадения.

### REPORT-2. Разделить четыре факта

1. Исполнитель закончил ход или был прерван.
2. Запрошенный отчёт доставлен полностью/частично/заблокирован.
3. Reviewer принял либо отклонил exact submission.
4. Текущие обязательные проверки применимы и успешны либо остаются неуспешными/неизвестными.

Не выводить один факт из другого. Успешно проведённое ревью может содержать reject. Сохранённый historical failed-run не должен вынуждать прятать историю в prose только ради полного финального ответа.

### REPORT-3. История checks и применимость evidence

Ввести структурированное append-only представление check runs с:

- `check_id`, `run_id`, ссылкой на criterion/контракт и ролью исполнителя;
- командой/настройками, окружением, временными границами;
- областью проверенных байтов: pinned commit/tree/archive/content digest и внешними непроверенными границами;
- фактическим исходом, ссылкой на сохранённый output, происхождением записи;
- явным отношением replacement/supersedes, если новый запуск удовлетворяет тому же актуальному требованию.

Точное размещение выбрать в существующем artifact/report слое; **не создавать вторую систему findings или универсальную платформу запуска тестов**.

Правила:

- Старый failed не становится passed и не исчезает. Новый passed — отдельный run.
- Совпадения имени проверки недостаточно для замены: требование, проверенные bytes и применимое окружение должны совпасть или различие должно быть явно рассмотрено.
- Непройденную текущую required проверку нельзя перенести в history без заменяющего evidence и тем самым получить success.
- История unexplained flake остаётся visible known issue даже после текущего passed; это не доказательство исправления причины.
- Результат, сообщённый участником, остаётся `participant_reported`. Хеш делает запись неизменяемой, но не доказывает, что команда реально запускалась. Только реально code-owned runner может маркировать собственное наблюдение как machine-observed.
- Author evidence не становится независимым reviewer evidence от повторного использования.
- Для старых отчётов без новых identity — legacy/unscoped, не выдуманные fingerprints.

**Приёмка:** B2-подобный кейс показывает accepted submission, полный отчёт, первоначальный failed, новый применимый passed и отдельное оставшееся flake-ограничение. Новая несовместимая версия байтов не использует прежний pass. Фальшивое supersedes на чужой run/criterion не снимает текущий failure.

**Измеримая оптимизация:** author проверил неизменяемый tree, затем создан commit с тем же tree — сохранить применимость без нового author full suite только ради commit timestamp. Если выполнение шло по mutable worktree и нельзя доказать неизменность входов, повтор не отменять. Независимое ревью и обязательные проверки объединённых байтов сохранить.

## 6. VIEW — компактный статус, допустимые действия и честная идентичность

**Приоритет: P1. Это изменение представления, не новая автономность.**

### VIEW-1. Разделить progress и полные материалы

На MCP/native поверхности сделать обычные list/get и ответы на mutations компактными. Полный план, отдельный шаг, большие evidence и история доступны явными запросами/страницами через существующий `tandem_work`.

Консервативный публичный контракт:

- `view=summary` — обычный progress по умолчанию;
- `view=plan` — полный договор для осмысленного agreement;
- `view=step` + `step_id` — разрешённые детали конкретного шага;
- `view=full` — явный полный view при необходимости;
- `history` — ограниченная страница событий без полных повторяющихся snapshots по умолчанию; полные исторические материалы запрашиваются явно;
- Markdown не дублирует JSON без отдельного запроса формата.

Согласовать окончательную wire schema до кода. Мигрировать все собственные потребители, которые ждут полный `plan/steps/markdown`; доменное состояние не урезать. Старые exact operation receipts сохраняют прежний смысл и fingerprint: новый параметр presentation не должен превращать точный legacy retry в другое действие или менять выдаваемое право.

Summary содержит как минимум: work/revision/plan_revision, заголовок, состояние, роль текущего участника, компактные шаги с зависимостями, все применимые blocker/recovery причины или явные ссылки на их страницы, exact submission IDs/commits, next actions и указатели на полные критерии. Не скрывать «неудобные» blockers ради лимита.

- Пагинация привязана к наблюдаемой ревизии; невозможность продолжить прежнюю страницу обозначается явно.
- Размерное ограничение сопровождается явным continuation/truncation descriptor, не молчаливым обрезанием критериев/ответа.
- Сначала permission/stage projection, затем сокращение. `full`, cursor, history, error и action hints не должны возвращать author material раньше разрешённого раскрытия.
- `get(wait_seconds>0)` ожидает изменение дешёвой revision/state projection, а не многократно строит и хеширует полный Markdown/evidence.

**Приёмка по E1:** на том же шестишаговом fixture summary не более **16 KiB UTF-8** тем же JSON serializer, при доступности всех значимых состояний/блокеров и полных данных по явным запросам. Это цель размера ответа, не обещание пропорционального снижения всей цены моделей. Отдельно проверить большие планы и pagination, не подгонять решение под шесть известных ID.

### VIEW-2. Возвращать структурированные next actions

Вместо одного общего текста вывести actor-/capability-aware допустимые действия и недостающие предусловия: action, step, kind/stage, exact submission, свежая revision, обязательные поля, blocked reason.

- Вычислять из существующей state machine, не из второго планировщика.
- Это подсказка, не разрешение на автоматическое выполнение. Сервер заново проверяет CAS, actor, stage и evidence.
- После собственного mutation использовать возвращённую свежую revision. Не требовать дополнительного get, если состояние уже получено и нет конфликта.
- При CAS conflict вернуть безопасную актуальную информацию без скрытого retry.
- Не объединять независимый report, compare и accept; не автоматически соглашаться с планом и не выбирать reviewer verdict.
- В hints не выдавать token, чужой receipt или author content.

**Приёмка:** owner видит claim/submit либо конкретную причину запрета; reviewer — report, затем optional compare и допустимый verdict. Чужой submission или неприменимый waiver не превращается в допустимый action. Exact retries не добавляют новые launches/events/effects.

### VIEW-3. Показывать реальный рабочий runtime и режим

В существующие scope/diagnostic/status-поверхности добавить идентичность **запущенного** Tandem, а не только версию исследуемого checkout:

- версия рабочего сервера и источник identity;
- поддерживаемый work/review protocol и digest фактически опубликованной schema для конкретной поверхности;
- installed immutable build identity, если она действительно известна; editable/unpinned — явно неизвестная точная идентичность;
- actual manual/managed режим данной попытки, наличие/действительность grant и границы продолжения после отключения;
- declared protocol и disclosure provenance текущего review;
- requested/effective/observed model отдельно, с источником.

Не вычислять «версию загруженного процесса» по файлам, которые могли обновиться уже после его старта. Не делать скрытый live provider probe. Не считать разные transport schema digests автоматической несовместимостью без учёта формата поверхности.

**Приёмка:** старый MCP, работающий с checkout новой версии, показывает обе идентичности и не заявляет новый протокол по README. Legacy/disclosed review не переименовывается. Рестарт/обновление предлагает безопасный путь без убийства активной работы и без автоматической миграции grants.

### VIEW-4. Разделить принятие и применение; дать простой итоговый отчёт

- `completed` — приёмка текущей интеграции.
- Применение/публикация — отдельные наблюдения или операторские receipts. При их отсутствии: **unknown/not_recorded**, не безусловное «не применено».
- Git-состояние читать только при явно запрошенной оценке; не запускать Git на каждом progress get. Наблюдение содержит expected/observed HEAD и время, не выдаёт разрешения на reset/merge.
- Из равенства HEAD и target не выводить, кто и каким способом выполнил apply. Внешние cherry-picks и публикация по сети не угадываются.
- Обычный отчёт через существующий CLI show/формат Markdown: договорённости, принятые шаги, reject→fix→accept, незавершённые причины, версии/режимы, ссылки на evidence и известная область затрат. Без новой веб-платформы и без LLM-пересказа по умолчанию.
- Учёт объединять только по однозначным task/attempt связям, каждый native turn один раз. Не парсить произвольный prompt как авторитетную привязку. Legacy без связи — unattributed/unknown. `provisional_artifacts` уже существуют: использовать их с действующей visibility policy.

**Приёмка:** E9 больше не выдаёт недоказанный отрицательный факт. Отчёт по новой контрольной работе можно получить без ручного SQL и без повторного модельного исследования; неизвестная стоимость Claude остаётся unknown, partial cost — подытогом.

## 7. RECOVER — безопасное продолжение и закрытие manual claim

**Приоритет: P1. Не строить generic retry engine.**

### RECOVER-1. Долговечная серверная привязка

Связать manual work attempt, exact claim receipt, originating native task/conversation и явно допустимого successor на host/server уровне. Использовать существующий механизм receipt/authentication; не создавать глобальный поиск секретов по actor.

- Привязка к работе не равна autonomous grant и не меняет mode/shell/model полномочия.
- Не переносить managed allow_* defaults на ручную работу так, чтобы они неожиданно расширили или отменили её отдельный согласованный контракт.
- Публичный recovery descriptor: attempt, source/submission, исходный task, состояние, разрешённые действия, ссылки на доступные уже сохранённые материалы, нужна ли остановка/reconcile. Без token и без восстановления секретного старого запроса в prompt.
- Необоснованная смена conversation/host owner не даёт credential даже при том же actor/work_id. Межсессионное восстановление — явный авторизованный путь; legacy без доказуемой привязки не присваивается автоматически.

### RECOVER-2. Отделить восстановление права отчёта от повторного исполнения

После failure законный участник может явно восстановить **тот же ещё действующий claim** и закрыть его по сохранённым доказательствам. Новые тесты, редактирование и модельный запуск не являются обязательной ценой восстановления bookkeeping.

- Exact retry не создаёт attempt, новую stage или перенос verdict на другой commit.
- Completed/fenced/expired claim не оживает. Uncertain effects и неподтверждённая остановка требуют существующего operator reconcile.
- Провайдерный `cyber_policy` сохраняется как provider-policy отказ. Не автоматически переформулировать запрос, переключать провайдера или повторять его для обхода ограничения. Допустимое административное закрытие уже имеющегося состояния не выдаётся за продолжение запрещённого исполнения.
- Не выбирать accept/reject по наличию артефакта автоматически: решение остаётся явным действием разрешённого reviewer.
- Все recovery/read/action surfaces сохраняют независимую stage projection.

**Приёмка:** ошибка после публикации finding, до verdict и без `tandem_finish`; существующий `provisional_artifacts` показывает разрешённый материал, авторизованное продолжение получает прежний attempt/receipt без ручной копии старого note. Закрытие не запускает модель/worker и не повторяет проверки. Чужой участник, иной submission, новая stage и retired capability отклоняются. Успешное возобновление обычного процесса — отдельный явно разрешённый сценарий, не побочный эффект чтения.

## 8. WAKE — детерминированная семантика уведомлений

**Приоритет: P1.**

Закрепить существующее: wake — повторяемая подсказка об изменении; authoritative состояние читается отдельно; ack может быть отложен. Не превращать best-effort в обещание синхронного исчезновения всех событий.

- Сделать deferred/busy acknowledgement различимым для внутренних consumers и диагностики, не блокируя `get`.
- Исправить именно тестовый контракт: детерминированно организовать producer/reader/SQLite interleavings вместо повторных полных прогонов и увеличения sleep.
- Без конкуренции наблюдение подтверждает уже существующий hint до revision R.
- При удержанном writer lock get возвращает актуальное состояние, hint может остаться; следующее предусмотренное observation после освобождения подтверждает его.
- Поздний emit уже прочитанной ревизии допустим как повторный hint; не даёт dispatch/claim/permission. Ошибка emit не теряет курсор.
- R не подтверждает R+1, другой work или owner. Reconnect начинает с явной синхронизации состояния, не с предположения «нет wake — нет изменений».

Для этой итерации не вводить второй durable watermark/очередь только ради полного отсутствия повторных hints. Такой stronger contract требует отдельного обоснования. Исходную intermittency не объявлять диагностированной, если новый сценарий лишь воспроизводит один допустимый путь, а не установленное первоначальное interleaving.

**Приёмка:** все перечисленные interleavings воспроизводимы без случайных sleeps; read остаётся неблокирующим; duplicates не меняют work state/attempts; preserved failure из истории остаётся в отчёте как исторический факт.

## 9. VERIFY — точность capability evidence и подготовка окружения

**Приоритет: P1 для корректности gate; P2 для устранения лишней инфраструктурной работы.**

### VERIFY-1. Усилить уже существующий abort probe

В `scripts/verify_omp.py` gate `parent_abort_prevents_late_child_delivery` сейчас использует неизменность request count и оставшиеся scripted steps, но не включает `parent_alive` в predicate. Конкретный принятый прогон подтверждал живой parent отдельным наблюдением; не выдавать это за новую доказанную поломку OMP.

Требование: положительный gate нуждается и в наблюдении живого parent до cleanup. Negative fixture с недоступным/остановленным parent не становится supported только из-за отсутствия поздних запросов. Сохранить различие abort и process-group cleanup; не включать helpers по одному gate.

### VERIFY-2. Разделить acquisition и исполнение compatibility probes

Прошлый Linux-run исчерпал срок на скачивании OMP ещё до запуска probes. Уже существующий `--omp` позволил использовать официальный проверенный бинарник без повторения остальных Linux checks.

- До bounded probes дать понятный preflight наличия/identity pinned binary и готовности окружения.
- Acquisition failure, probe failure и unsupported capability — разные результаты.
- Описать повторное использование того же проверенного binary и isolated environment через существующие флаги.
- Не увеличивать production deadline, не отключать checksum и не встраивать универсальный downloader/chunk-retry subsystem только из-за этого случая.
- Cold failure не перезаписывает исторический passing report и не считается успешной совместимостью.
- Сохранить границы macOS/native OMP, Linux/container, hosted CI и неподтверждённых upstream сценариев.

**Приёмка:** неверный supplied binary отклоняется по pin; acquisition timeout не помечает probes пройденными; повтор только необходимой compatibility-фазы не требует заново запускать уже применимые tests/package checks. Штатные команды и настройки пользователя не меняются.

| A09 | Старый server/new checkout не выдаётся за новый working runtime; manual/disclosed протокол видим |

| A11 | Чужая session, fenced attempt и другой submission не получают право продолжения; legacy связь не выдумана |

| A13 | Completed card без apply receipt не утверждает «не применено»; отчёт отдельно показывает known/unknown application state |

| A16 | Acquisition failure не считается probe pass; supplied binary проверяется по pin |
| A17 | Полный bounded shared flow на **новом установленном runtime** выполняет report/compare/verdict, а не только тестирует новый код из старого клиента |

Для A17 использовать отдельную fixture-карточку и изолированное окружение. Реальные OMP/Claude CLI с scripted localhost model fixture допустимы для проверки транспорта и границ; это не измерение качества живых моделей. Платный или внешний модельный smoke — только с отдельным явным разрешением и отчётом расхода. Не прерывать текущие пользовательские сессии ради обновления клиента.

## 12. Проверки, документация и выпуск

- Для подтверждённого дефекта сохранить содержательное воспроизведение: fails before / passes after. Не писать тесты, сравнивающие текст исходников, набор внутренних вызовов или формулировку сообщения вместо поведения.
- Не лечить intermittent зелёными повторами, sleep/timeout padding или снятием защиты. Контрактно неверный assertion заменить правильным наблюдаемым сценарием с объяснением, не скрыв историю отказа.
- После объединения — один полный проектный прогон, lint/format, wheel/archive/installation/manifests и реальный pinned OMP compatibility scenario. Промежуточно — прицельные проверки изменяемых границ. Независимый reviewer выполняет собственную проверку; author pass ему не подменяет evidence.
- EN/RU/ZH README, guide и skills должны объяснять компактный контракт, новые projections, runtime identity, recovery и границы independent review. В changelog не обещать универсальную автономность/изоляцию/экономию.
- Проверить все MCP/native/CLI потребители изменённой формы, включая restricted review server, diagnostics, result views и приёмку managed attempts.
- Номер релиза выбрать после проверки совместимости. Это ТЗ не фиксирует заранее «3.6.0» и не разрешает перезаписать v3.5.0.
- Старые публичные теги и архивы не изменять. Принятый результат не публиковать/apply автоматически.

## 13. Что не входит в эту итерацию

- Production scout/sonic и этапы C–F прежнего большого ТЗ: пять обязательных helper gates всё ещё не удовлетворены.
- Автоматическая смена модели/thinking или провайдера ради цены, обход provider policy, generic retries.
- ОС-песочница, облачный orchestrator, новая веб-платформа, дополнительный MCP на каждую роль.
- Автоматический judge, который соглашается с планом, разрешает blocker или принимает код за участников.
- Новая система findings рядом с существующей, полная замена WorkStore/ReviewStore либо отдельный каталог моделей.
- Отмена самостоятельного reviewer/full integration checks под предлогом экономии.
- Повторное открытие исправленных B2 F1–F5, прежних A1/A2/B1 задач или уже исправленного `_view` падения на model-selection ошибке.

## 15. Что вернуть пользователю после реализации

Краткий итог по пакетам SAFE/REPORT/VIEW/RECOVER/WAKE/VERIFY, exact integrated commit, независимая приёмка и матрица A01–A18: что реально выполнено, чем проверено и какие ограничения остались. Отдельно — размер progress view до/после, административные действия без новой модели, полный/частичный расход и его область, фактическая версия исполняющего клиента.

Не обещание «станет дешевле», а проверяемый результат. Не новый бесконечный план, а завершённая ограниченная итерация с сохранёнными границами безопасности и правдивыми свидетельствами.
