# Единое ТЗ: помощники OMP и доработка совместной разработки в OMP Tandem

Статус: техническое задание на реализацию, не описание уже выпущенных возможностей.
Основа: пользовательское ТЗ «Модели-помощники внутри OMP через omp-tandem» и замечания к OMP Tandem 3.4.0.
Проверенная база: релиз f3954e667fd287095e03e208859fbc62b2899890; при подготовке документа main — 40238eeb01e02cdf1bd99c3a404df35fdcf6a7af.
Дата проверки: 11 сентября 2026 года.
Формат работы: несколько последовательных изменений с отдельной проверкой границ, а не один большой непроверяемый коммит.

## 0. Решение и границы достоверности

Идею из исходного ТЗ принять: основной OMP-исполнитель решает содержательную задачу, а штатные помощники OMP выполняют объёмное исследование и явно ограниченные механические изменения в отдельных контекстах. Claude Code остаётся пользовательским интерфейсом. Не создавать самостоятельные API-клиенты, отдельный MCP-сервер на модель или второй справочник OMP-моделей. [S0]

Добавление помощников не должно ослабить независимость ревью, расширить полномочия, скрыть расходы либо нарушить остановку и восстановление. Поэтому сначала устраняются пересечения с существующими механизмами 3.4, затем включается делегирование.

В документе различаются:

- Факты текущей базы: существующие механизмы и ограничения, подтверждённые исходным ТЗ и просмотренными исходниками.
- Новые требования: целевое поведение, которое нужно реализовать и проверить.
- Условия совместимости: свойства OMP, которые нельзя считать обеспеченными одним YAML-файлом или инструкцией модели.

Здесь не утверждается, что выполнены live-запуски выбранных пользователем моделей, измерена экономия или уже доказана безопасность всех путей делегирования. Модельные идентификаторы ниже — пользовательский пример конфигурации, а не подтверждение доступности на конкретном аккаунте.

## 1. Цель и пользовательские сценарии

### 1.1. Основной сценарий: работа через Claude Code

Пользователь один раз настраивает роли через setup-процесс Tandem, разрешает делегирование и дальше обращается к Claude обычным языком. Для каждой задачи ему не требуется запускать интерфейс OMP, переключать модели, управлять сессиями помощников или координировать каждое чтение.

Целевой поток:

```
Пользователь → Claude Code → OMP-родитель
                               ├─ scout: исследование в отдельном контексте
                               ├─ sonic: разрешённые механические изменения
                               └─ собственный анализ, решение и проверка
                         ← результат, доказательства, ограничения и расход
```

«Без ручного управления OMP» не означает автоматическую авторизацию без участия пользователя. Первичная установка и вход выполняются поддерживаемым OMP способом, с явным участием пользователя там, где оно необходимо. Tandem не копирует credentials в свои настройки, задачи или отчёты. [S0; S2]

### 1.2. Совместная разработка и автономный контроллер

Существующие tandem_work, версии плана, независимый исполнитель/проверяющий, worktrees, блокировки и явный apply сохраняются. Помощник OMP является внутренним исполнителем конкретной OMP-попытки, а не третьим участником приёмки общей задачи. [S3; S4]

Отдельно разрешённый автономный контроллер продолжает управлять своими попытками независимо от закрытия интерактивного чата. Обычная задача, принадлежащая закрытому MCP-клиенту, должна остановиться вместе со своими помощниками. Эти два жизненных цикла не смешивать.

### 1.3. Что считать успехом

Основной контекст получает необходимые факты вместо всего предварительного чтения. Независимый проверяющий по-прежнему сначала формирует свою оценку. Пользователь видит фактические модели, полномочия, блокировки и полный доступный учёт расходов. Ранее работавшие сценарии без помощников не ухудшаются.

Экономия контекста — измеряемая гипотеза. Экономия времени, стоимости и квоты подписки не обещается до соответствующих измерений.

## 2. Что сохранить и что исправить

| Область | Текущая опора | Требуемое изменение |
|---|---|---|
| Выбор OMP-модели | ExecutionOptions, профиль, model/thinking | Использовать повторно; не создавать параллельный механизм |
| Роли помощников | Штатные modelRoles, task.agentModelOverrides | Безопасное разрешение ролей, фиксация настроек и отдельные контексты |
| Shared-task review | Отдельный reviewer, точный submission | Не раскрывать авторскую интерпретацию до независимого этапа |
| Автономный Claude | В адаптере явно задан sonnet | Отдельный, предсказуемый выбор модели Claude |
| Бюджет | Резервирование попыток | Отделить бюджет попытки от max_launches; учитывать дерево помощников |
| Разрешение тестов | --allow-tests открывает shell | Явное название --allow-shell, совместимость старого флага |
| План | Консервативный сброс после изменения | Анализ затронутых шагов и явное переутверждение незатронутых результатов |
| Blocker | Другой участник не может его просто снять | Сохранить правило при смене плана, добавлении помощников и смене стадии |
| Управление | Подробные данные и операторский CLI | Краткий человеческий статус и два отдельных пути входа |
| Проверка выпуска | CI, реальные бинарники, локальные fixtures | Воспроизводимые проверки нового дерева исполнения и честный live-кейс |

Фактическая основа этой таблицы: исходное ТЗ, код адаптеров, карточек задач, рабочего процесса и журнал выпуска. Это не список уже реализованных изменений. [S0–S6]

## 3. Обязательная проверка совместимости до включения помощников — G0

### 3.1. Зафиксировать реальную базу

До изменения кода прочитать текущие commit/tag, совместимую версию OMP, ревизию omp_rpc, реальные схемы инструментов и конфигурации. Если main ушёл вперёд, сопоставить изменения с этим ТЗ; не переносить выводы о 3.4 на новую реализацию автоматически.

Отдельный артефакт docs/helper-compatibility.md должен перечислить проверенные версии, механизм каждой гарантии и тест, который её проверяет. Использовать публичные средства поддерживаемой версии OMP. Не обходить недостающий механизм вложенным CLI через shell, приватной monkeypatch-подменой или прямым API модели.

### 3.2. Проверить не только запуск task

Проверка должна охватывать:

- Реальное применение agentModelOverrides, алиасов ролей и thinking; различие запрошенного значения и фактической настройки провайдера.
- Наследование или явное ограничение инструментов дочерней сессии, включая альтернативные пути через eval, hub, расширения и повторное оживление сессий.
- Изоляцию child-context, формат итогового результата, async-инъекции, доступ к agent:// и history://.
- Передачу отмены, дедлайна и закрытия владельца всему дереву; запрет поздних результатов и повторного оживления после остановки.
- Полноту и область native usage: включает ли родительский показатель дочерние вызовы.
- Обнаружение пользовательских/проектных определений агентов и перечитывание настроек во время задачи.
- Стартовые, retry-, overflow-, prewalk- и advisor-механизмы, способные изменить модель или породить дополнительные вызовы.
- Возможность ограничить снимок ревью, а не только рабочий каталог.

В документации OMP 18.1.13 описаны перечитывание настроек при task-preflight, отдельное формирование инструментов помощника, фоновые результаты и жизненный цикл idle/parked. У bundled scout и sonic указано medium как исходное thinking-настройка. Поэтому :low, фиксированный снимок конфигурации и остановка дерева требуют проверки на фактическом пути запуска. Это не утверждение, что пользовательский override low обязательно не работает. [S7–S10]

### 3.3. Условия открытия функций

Без доказанного ограничения прав task в соответствующем режиме остаётся недоступным. Выводить конкретную причину delegation_unavailable, а не успешную диагностику с неработающей функцией.

Допустимо первым этапом отключить делегирование в think и immutable-review, как предусмотрено исходным ТЗ. Исследовательский scout и пишущий sonic нельзя объявлять готовыми, пока не пройдут их обязательные проверки. Если требуется изменение upstream OMP, оформить его явно и обновить проверенную версию; отказ функции не считать реализацией требования.

## 4. Конфигурация и предсказуемый выбор моделей — CFG

### 4.1. Один справочник OMP-ролей

Сохранить пользовательскую настройку вне каталога плагина. Для OMP использовать штатное активное расположение конфигурации, учитывая существующий config.yaml и переопределённый каталог OMP, а не всегда писать в жёстко заданный путь. Существующие несвязанные настройки сохранять. [S0; S7]

Пример желаемых ролей из исходного ТЗ:

```yaml
modelRoles:
  default: openai-codex/gpt-6-astra
  smol: openai-codex/gpt-5.3-codex-spark:low

task:
  agentModelOverrides:
    scout: "@smol"
    sonic: "@smol"
    task: openai-codex/gpt-6-astra:high
    reviewer: openai-codex/gpt-6-astra:high
    security-reviewer: openai-codex/gpt-6-astra:high
```

Этот YAML сохраняет замысел пользователя, но сам по себе не включает делегирование в текущем Tandem. Корректность разрешения селекторов и фактический low принимаются по G0 и тестам, а не по наличию строки в файле.

Политика Tandem может отдельно хранить разрешение делегирования, пределы и допустимые роли. Она не должна дублировать OMP-каталог конкретных моделей. Временный неизменяемый снимок эффективной конфигурации — производные данные задачи, а не второй пользовательский справочник.

### 4.2. Настройки родителя и помощников не смешивать

execution.model меняет только родительскую OMP-модель. Профиль родителя не навязывает thinking помощникам. Определение роли не даёт разрешения её запускать: разрешённые роли и модельная маршрутизация проверяются отдельно.

При первом включении автоматического делегирования разрешить scout и, только в подходящем режиме, sonic. Сильные роли task, reviewer, security-reviewer остаются настраиваемыми, но их автоматический запуск требует явной разрешающей политики и бюджета. Внутренний reviewer не заменяет второго участника shared-task приёмки.

Не поддерживаемый моделью low не выдавать за применённый. Диагностика показывает поддерживаемое и фактическое значение; для пользовательского требования точного low недоступность такого режима блокирует роль до явного изменения настройки.

### 4.3. Модель автономного Claude

Убрать безусловное --model sonnet из адаптера как скрытую политику. Добавить отдельный операторский выбор модели Claude; предложенное имя — --claude-model. Существующий --model сохраняет значение OMP-override; допустим более ясный синоним --omp-model.

Нельзя угадывать модель по последнему открытому чату, заимствовать чужую сессию или утверждать, что автономная попытка наследовала интерактивный выбор. Без явного значения допустим документированный старый default, но он должен быть показан до разрешения запуска.

Имена новых параметров здесь — проектируемый интерфейс. Они не должны появляться в инструкции пользователю как уже доступные до реализации.

### 4.4. Неизменяемый снимок эффективных настроек

До первого модельного запроса зафиксировать:

- модель и thinking родителя;
- разрешённые роли, разрешённые определения агентов и их хеши;
- фактически разрешённые модельные селекторы/настройки помощников;
- права, источник данных, ограничения вложенности и параллельности;
- fallback-политику и учётные пределы;
- версии OMP/SDK и идентификатор снимка настроек.

Все помощники одной задачи используют один снимок. Правка глобального конфига или агентского файла не меняет последующих помощников уже выполняющейся задачи. Динамическое обнаружение OMP не должно незаметно отменять это правило.

Для продолжения диалога default — сохранённый снимок прошлого хода. Его обновление выполняется явно перед новым ходом, когда прежнее дерево остановлено. Обновление конфигурации не расширяет права диалога. Для managed work настройки закреплены разрешением контроллера; изменение требует нового разрешения, а не только правки YAML.

Показывать отдельно requested, resolved и наблюдённое actual; не подставлять запрошенное имя в поле фактически подтверждённой модели. Если immutable provider snapshot неизвестен, прямо указывать, что использован изменяемый алиас.

### 4.5. Setup без ручной рутины

Setup читает только относящиеся к моделям/ролям разрешённые настройки, показывает diff и сохраняет его после явного согласия. Запись — атомарная с проверкой конкурентного изменения и резервной копией. Не переписывать всю конфигурацию с потерей несвязанных полей.

Разделить локальную диагностику и live-проверку доступа: последняя может расходовать средства/квоту и требует разрешения. Обновление плагина не меняет пользовательские роли и не включает делегирование автоматически.

## 5. Права помощников, полномочия и жизненный цикл — HELP

### 5.1. Полномочия определяются исполнением

Эффективные права помощника — пересечение режима родителя, роли, операторского разрешения и закреплённого источника/области файлов. Одного промпта «не изменяй файлы» недостаточно.

| Родитель/режим | Допустимые помощники |
|---|---|
| think | По умолчанию отключены; включение отдельно допустимо только без доступа к проекту и shell |
| analyze | scout с чтением/поиском в разрешённой области, без записи и shell |
| work без shell | scout; sonic только с разрешёнными edit/write и точными файлами |
| work с shell | Только дополнительно разрешённые shell-действия; scout всё равно остаётся без shell |
| Managed implementation | Только область и полномочия конкретной попытки |
| Managed reviewer | Без пишущих помощников; доступ только к версии и представлению своей стадии |
| Immutable snapshot review | Тот же snapshot-reader и стадия либо делегирование явно отключено |

Проверять запреты также для незаявленного прямого вызова инструмента, а не только его отсутствия в описании для модели. Запрет task у потомка должен распространяться на альтернативные способы запуска/оживления агентов.

### 5.2. Что запрещено помощнику

Помощник не получает credentials внешней задачи, общий MCP координатора, полномочия agree/claim/accept/reject/propose/apply/authorize/reconcile общей карточки или доступ к произвольной истории проектов. Он не завершает внешнюю задачу через родительский tandem_finish, не отправляет вопросы Claude напрямую и не подтверждает работу родителя.

Вопрос помощника возвращается родителю; родитель использует существующий канал уточнений. Итог помощника принимается через штатный дочерний механизм OMP и привязывается к его собственному ID.

Ограничения worker.yml на провайдеры обнаружения, импорт MCP и общую память сохранить. Проверить также проектные .omp-определения, aliases, skills, extensions, env overrides и вспомогательные модели. Нельзя разрешить широкий импорт конфигурации ради одного scout.

### 5.3. Управление файлами

Для sonic передавать конкретное механическое изменение, точные файлы, критерии и исходные хеши. Архитектурное решение или недостающий продуктовый выбор возвращаются родителю, а не угадываются помощником.

Два пишущих помощника и родитель не изменяют одновременно одни и те же файлы. Передача владения дочерней работе явная и ограниченная по времени. Родитель может выполнять независимую работу либо ждать; возврат владения происходит после подтверждённого завершения.

Изменения проверяются до продвижения результата в shared-task submission. Неожиданные файлы, устаревший источник или неполный результат не принимаются автоматически. Механический помощник не выполняет самостоятельный commit/merge/apply.

Worktree и проверка изменённых файлов не являются ОС-песочницей. При разрешённом произвольном shell нельзя обещать предотвращение всех внешних файловых/сетевых эффектов. Без доказанной инструментальной границы конкретный helper-режим не включать.

### 5.4. Вложенность и пределы

Начальная политика: один уровень помощников, максимум два одновременно у родителя. Дополнительно нужен проектный предел суммарно активных помощников, чтобы несколько OMP-родителей не умножали fan-out незаметно; предлагаемый default — два помощника на проект.

Количество запусков также конечно. В первой реализации предложенный default — не более четырёх запусков помощников на одну внешнюю OMP-задачу; effective limit показывается в диагностике и может быть изменён явной политикой. Это новый лимит, не переопределение смысла существующего max_launches автономных попыток.

Ожидающий помощник не занимает вычислительный слот до запуска. Ожидание родителем ребёнка не должно создавать взаимную блокировку планировщика. Отмена удаляет также ожидающие запуски. Повторное оживление дочерней сессии не обходит ни лимиты, ни разрешение, ни дедлайн.

### 5.5. Остановка всего дерева

Дедлайн помощника не позже дедлайна родителя. В управляемом режиме также действует deadline разрешения контроллера. Монотонные часы используются для текущего исполнения; сохранённые дедлайны перепроверяются после восстановления.

Остановка родителя запрещает новые дочерние вызовы, отзывает их рабочие полномочия, отменяет модельные запросы и завершает принадлежащие дереву процессы/фоновые jobs. Финальное успешное завершение родителя невозможно, пока его помощники продолжают исполняться.

Если подтверждения остановки нет, результат — неопределённое завершение/recovery_required, а не успех. Повторный запуск требует существующей процедуры reconciliation. Поздний отчёт не продвигается в актуальное состояние; сохраняется только как исторический артефакт.

Критическое различие: закрытие интерактивного MCP останавливает только его собственное дерево. Оно не отменяет ранее отдельно разрешённый detached controller. Остановка/отзыв/истечение разрешения самого контроллера останавливает все принадлежащие ему попытки и их помощников.

## 6. Контекст и доказательные отчёты — CTX

### 6.1. Постоянная политика родителя

Объёмный поиск, составление карты файлов и извлечение фактов поручать scout. Не запускать помощника ради одного короткого чтения. Родителю не повторять всё исследование без причины, но разрешить адресную проверку критического кода и сомнительных выводов.

sonic использовать только для однозначных ограниченных изменений. Сложные решения и принятие результата остаются у основной модели и соответствующего независимого reviewer. Эта политика включается после однократной настройки и не требует повторять её Claude в каждом запросе. [S0]

### 6.2. Передаваемый контекст

Передавать вопрос, границы поиска, требования, известные факты, обязательные ограничения и допустимые ссылки. Не копировать всю историю, ответы прежних неподходящих ролей, credentials или авторскую интерпретацию в независимый этап ревью.

Для одного helper-запуска использовать отдельную историю. Переключение GPT-6 → Spark → GPT-6 в одной истории не считается реализацией изоляции.

### 6.3. Формат результата

Результат должен содержать status, краткое резюме, факты с источниками, область фактического поиска, неизвестные вопросы и ссылки на расширенные артефакты. Статусы: выполнено, частично, заблокировано, ошибка, отменено; отображение на native статусы документировать.

Ссылка на код включает path, диапазон строк и идентификатор версии: commit/blob/content hash либо review snapshot. Номер строки без версии недостаточен. Для не-Git источника использовать сохранённый хеш прочитанных байтов; изменение файла делает вывод требующим перепроверки.

Предлагаемый пользовательский default для автоматически возвращаемого отчёта: до 6000 Unicode-символов, до 12 основных фактов и короткие выдержки до 400 символов каждая. Это ограничение вывода, не гарантия числа токенов. При превышении сохранять полный отчёт в артефакте и явно показывать truncated/ссылку; не терять ошибки и блокеры молча.

Полный transcript, файлы и промежуточные журналы не инъецируются автоматически в историю родителя — ни в обычном результате task, ни в async-completion, ни при fallback или обработке ошибки. Проверять фактические сообщения, передаваемые модели.

Фраза «не найдено» означает «не найдено в указанной области при указанных проверках», а не «во всём проекте отсутствует». Модельные выводы и наблюдаемые факты различать. Содержимое артефактов не является инструкцией изменить роли или права.

### 6.4. Изоляция исследования двух участников

Scouts исполнителя и независимого проверяющего запускаются отдельно. Отчёт помощника исполнителя не используется как готовая независимая база reviewer. Допустимо совместно использовать неизменяемые исходные байты и необходимые проверяемые факты с происхождением, но не скрыто подменять ими независимое исследование.

## 7. Independent-first в shared-task review — REV

### 7.1. Отдельные стадии

Сохранить низкоуровневый review-сценарий и распространить его порядок раскрытия на управляемую приёмку:

```
Неизменяемый submission + требования + необходимые исходные материалы
  → независимая оценка отдельного reviewer
  → сохранённый полный независимый отчёт
  → раскрытие отдельно сохранённого объяснения автора, если оно есть
  → не более одного сравнения
  → accept / reject / block с конкретными основаниями
```

Возможность перехода проверяет runtime. Сообщение «я подумал независимо» не заменяет сохранённую стадию. Частичный, заблокированный, неструктурированный или неуспешный независимый результат не открывает сравнение/приёмку автоматически.

Успешный отчёт может содержать серьёзные дефекты. success стадии означает корректно полученный отчёт, а не разрешение принять код. Отклонение или блокировка допустимы уже на основании независимых результатов; раскрытие автора не требуется только ради отказа.

### 7.2. Ограничить все каналы раннего раскрытия

Разделить сырые исходные материалы и авторскую интерпретацию. До завершения независимого этапа закрыть объяснения исполнителя во всех ответах _prompt, tandem_work get/list/history, событиях, артефактах, checkpoints, диагностике и helper-контексте. Одна фильтрация начального промпта недостаточна.

Предоставлять ограниченное представление по доверенному attempt/role/stage, а не по аргументу модели reveal_author=true. Помощник reviewer наследует то же представление. Прямое чтение полного work-* состояния или авторских логов через обычные файловые инструменты тоже не должно обходить границу.

Если существующие native инструменты не позволяют обеспечить это представление, использовать поддерживаемый источник/reader с проверкой разрешений либо оставить данный вариант ревью без помощников/без недоказанного обещания независимости. Не называть промптовый запрет технической гарантией.

Требования и заранее согласованный план доступны reviewer. Код может раскрывать замысел; абсолютная «слепота» не заявляется. Сырые результаты проверок выдаются с происхождением и ограничениями, но не вместе с авторским выводом о правильности.

### 7.3. Blocker и разногласия

Сохранить существующее правило: нерешённый blocker запрещает продвижение соответствующего шага; снять его может автор блокировки или оператор с конкретным resolution и evidence. Другой участник не может снять возражение своим согласием. Помощник сообщает возражение родителю, но не получает внешние полномочия приёмки.

Изменение плана, удаление шага, повторная попытка и перевод между стадиями не должны бесследно удалять blocker. Сохранить его связь со старой версией и потребовать явного решения автора/оператора: остаётся актуальным, разрешён новыми доказательствами либо потерял применимость по указанной причине. Удаление шага переносит нерешённый вопрос на карточку, а не очищает его.

Политика для содержательного конфликта: сформулировать две гипотезы, контрдоказательство, нарушаемый критерий и минимальную различающую проверку. Если продолжение зависит от недостающего пользовательского требования или разрешения, запросить решение человека. Не считать серьёзность, указанную моделью, доказательством дефекта.

В этот выпуск не входит обещание универсального автоматического классификатора «любое опасное контрдоказательство → обязательный человек». Явная блокировка обеспечивается кодом; решение, что текст требует блокировки, остаётся ограничением текущей архитектуры. В документации назвать эту границу прямо.

### 7.4. Точность приёмки

Приёмка связывается с планом, точным submission, snapshot, reviewer и сохранёнными стадиями. В управляемом режиме она фиксируется только после успешного завершения reviewer и проверки неизменности его материалов. Старое одобрение не применяется к новым байтам. Внутренний помощник исполнителя не может считаться distinct reviewer.

## 8. Бюджеты и фактический расход — BUD

### 8.1. Разделить три ограничения

Общий бюджет разрешения, максимальный бюджет одной попытки и число внешних запусков — разные параметры. Не вычислять потолок попытки автоматически как total / max_launches.

При резервировании попытки:

```
доступно = общий_лимит − известный_расход − активные_резервы
резерв_попытки = min(явный_лимит_попытки, доступно)
```

Если пользователь не задал лимит попытки, показать явный вычисленный default в предварительном просмотре разрешения. Значение не должно зависеть от увеличения max_launches. Не отдавать весь остаток первой параллельной попытке незаметно: политика разбиения резервов между готовыми работами фиксируется и показывается до запуска.

Предлагаемые названия новых параметров: --max-attempt-cost-usd, отдельные лимиты helper-параллельности/запусков. Финальный интерфейс может быть проще, но семантика должна оставаться раздельной и проверяемой.

### 8.2. Родитель и дети используют один резерв

Родительская попытка не получает полный бюджет плюс дополнительные независимые деньги для помощников. Все дочерние запросы, retries, fallback и связанные вспомогательные модельные вызовы учитываются внутри её дерева и общего grant.

Перед каждым helper-запуском резервировать его долю из доступного остатка дерева атомарно. Если OMP не позволяет обеспечить необходимый учёт и остановку на реальном пути, автономное делегирование не включать. Нельзя подменять реальный контроль лимитом, который только написан в промпте.

Существующий max_launches продолжает считать внешние managed attempts. Helper-запуски показываются отдельным конечным счётчиком и также подчиняются времени/расходу. Смена модели и оживление helper не обходят счётчики.

### 8.3. Учёт без двойного сложения

Для каждого узла показывать собственные затраты и область счётчика: exclusive либо inclusive of children. Сохранять происхождение и идентификаторы запросов там, где их предоставляет native runtime.

Если OMP уже включил расходы помощников в родительский total, не прибавлять их снова. При отсутствии request IDs использовать документированную native-агрегацию; не сопоставлять произвольно запросы по близким числам токенов. Неполный учёт остаётся partial/unknown.

Разделять tokens, provider-reported cost, measured duration и subscription quota. Не превращать неизвестную цену в ноль. Не выдавать клиентскую стоимость за счёт провайдера или токены за точный расход лимита подписки.

В обычной интерактивной задаче неизвестность показывается в результате. В автономном режиме сохранить существующее консервативное поведение: неизвестная стоимость блокирует новые запуски и переводит работу в требующее оператора состояние. Успешный итог дерева не публиковать до учёта либо явной фиксации неизвестности всех его детей.

### 8.4. Fallback

По умолчанию недоступность Spark или требуемого thinking не вызывает незаметный переход на GPT-6. Вернуть структурированную ошибку роли. Пользователь может заранее разрешить конкретную альтернативу; её выбор не выходит за резерв, права и visibility стадии.

Проверить стартовую маршрутизацию, retries, overflow, auto-thinking, prewalk, advisor и дополнительные модельные сервисы. Необъявленные смены модели и дополнительные платные помощники выключить либо включить в явную политику и учёт.

Допустима работа родителя без помощника после явного решения продолжить в таком режиме. Это отмечается как «делегирование не состоялось», а не как скрытая успешная замена роли.

## 9. Разрешение shell — PERM

Ввести --allow-shell как основное понятное имя существующего разрешения произвольного shell. Сохранить --allow-tests как совместимый deprecated alias с предупреждением о реальных правах. Старые сохранённые grants читаются без расширения полномочий; неоднозначные данные требуют проверки, а не автоматического разрешения.

Предварительный просмотр показывает edit/write, shell, сетевые возможности и отсутствие ОС-песочницы. Название «тесты» не должно создавать впечатление ограниченного sandbox-runner.

При shell=false блокируются также вызовы shell через helpers, eval, nested CLI и повторно загруженные extensions. Read-only reviewer не получает пишущего помощника даже при отдельно разрешённых shell-проверках.

Операторский CLI — отдельная поверхность разрешений, но не криптографическое доказательство присутствия человека при произвольном shell под тем же OS-пользователем. Сильную внешнюю изоляцию и необходимое ей разделение учётных данных не заявлять как часть этого выпуска.

## 10. Изменение плана без потери проверенной работы — PLAN

Сохранить безопасный default: новая содержательная версия не наследует старую приёмку автоматически. Перед изменением показывать affected steps, зависящие шаги, сохранённые результаты и необходимость нового разрешения.

Вычислять fingerprint каждого шага по goal, acceptance, constraints, owned_files, ролям, входным данным и версиям принятых зависимостей. Изменение глобальных критериев или общего исходного baseline по умолчанию затрагивает весь план. Изменение шага затрагивает его и транзитивных потребителей.

Для незатронутого результата допускается явный перенос подтверждения: оба участника согласуют новый план, назначенный reviewer создаёт новую запись о применимости старого неизменяемого submission к новой версии. Старую запись не редактировать и не переименовывать в свежую проверку. Указать carried_from и основания, а не выдуманный повторный запуск тестов.

Перенос запрещён при изменении входных зависимостей, обязательных критериев, исходных байтов, unresolved blocker или неопределённой попытке. Артефакты всегда сохраняются, даже когда повторное использование приёмки запрещено.

Любое расширение прав, файлов или бюджета требует нового операторского разрешения. Перенос результата не переносит grant автоматически. Старые активные попытки не публикуют в новую версию плана. Если безопасная неизменность не доказана, использовать существующую полную переоценку.

## 11. Понятный статус и два пути входа — UX

Не строить отдельную веб-платформу в рамках этой задачи. Использовать существующую карточку, Markdown и CLI.

В README выделить два входа: «Проверить подготовленный коммит» и «Выполнить общую задачу двумя агентами». Делегирование помощникам показать как внутреннее дополнение OMP, а не как третий набор ручных команд.

Перед автономным запуском показывать подтверждаемое описание: проект, plan revision, исходный commit, модели обоих участников и helper-роли, права, конечные лимиты, что произойдёт при unknown cost и как остановить работу. Изменение любого значимого параметра отменяет актуальность старого предварительного просмотра.

Краткий статус должен отвечать:

- Что выполняется и кем?
- Какая модель реально используется?
- Какие помощники активны, что им поручено и сколько уже израсходовано?
- Почему остальные шаги ждут?
- Есть ли содержательный вопрос человеку или техническое recovery?
- Кто поставил blocker и кто вправе его снять?
- Что уже принято, что устарело и что ещё не применено?
- Какое одно следующее действие требуется от пользователя?

Различать blocked, waiting_input, waiting_dependency, budget_exhausted, cost_unknown, paused, recovery_required и completed_not_applied. Не маскировать причины общим «агент думает».

Поддержать машинный JSON и короткий человекочитаемый вывод без поломки существующих скриптов. Старый модульный CLI остаётся рабочим; удобная консольная точка входа может вызывать тот же код, не угадывая путь приватного plugin cache.

Сводка не должна бесконечно разрастаться полными transcripts. История и большие отчёты доступны адресно и с постраничным чтением; фильтрация независимого ревью применяется и здесь.

## 12. Миграция, совместимость и откат — MIG

При обновлении делегирование по умолчанию выключено. После явной настройки оно работает автоматически в разрешённых случаях. Переключатель disable возвращает прежний путь одной OMP-модели без потери старых данных.

Сохранить чтение старых задач, артефактов, grants и результатов 3.4. Не создавать видимость independent-first для исторических shared-task reviews, которые выполнялись по старому порядку раскрытия. Показывать protocol version и фактический тип свидетельства.

Для старого grant не пересчитывать лимиты активной попытки на лету. Новая бюджетная политика применяется только к новому разрешению. Миграция базы не возобновляет старые процессы и не сбрасывает blockers/recovery_required.

Перед миграцией проверять проектную принадлежность, версию схемы и отсутствие конкурирующего контроллера. Предусмотреть проверенную резервную копию SQLite с учётом WAL. Откат к старому приложению после изменения схемы не обещать без теста; при несовместимости использовать сохранённую копию после подтверждённой остановки.

Выпустить новую версию с корректными тегом, архивом, wheel, manifests и документацией. Не переписывать опубликованный тег 3.4.0 ради зелёного CI. Отдельное ранее сделанное исправление теста должно попасть в новый выпуск. Номер релиза выбирать по реальному объёму изменений.

### 14.1. Три разных уровня свидетельств

Детерминированные тесты: состояние, модельная маршрутизация, ограничения, ошибки, учёт и восстановление. Они не доказывают качество решений моделей.

Real-binary fixture: настоящий Claude/MCP, OMP и SDK, модельные HTTP-ответы выдаёт локальный fixture. Сохранять inputs/outputs, фактические инструменты и попытки запрещённых действий. Проверяется механика; scripted token/cost не публикуются как пользовательская экономия.

Live-проверка по отдельному разрешению: выбранные пользователем parent/helper модели выполняют реальное исследование; родитель использует факты, sonic делает разрешённое изменение. Сохранить версии, фактические настройки, области контекста, расходы обоих участников и ошибки. При недоступности аккаунта отметить live-пункт как не выполненный, а не заменять его fixture-успехом.

### 14.2. Измеренный случай совместной разработки

Подготовить один небольшой реальный кейс: согласованный план → два независимых модуля → cross-review → замечание/исправление либо честно зафиксированное отсутствие замечания → при необходимости blocker и его разрешение → финальная интеграция → отдельный apply.

Не искусственно приписывать модели находку и не выдавать заранее прописанные ответы за живую работу. Сохранить неудачные попытки и стоимость полного процесса. Этот кейс не заменяет четырёхвариантный сравнительный benchmark.

Для проверки контекстной экономии отдельно сравнить одинаковую ограниченную задачу с helpers и без них: качество ответа, parent-context, суммарные input/output tokens всех моделей, wall time и доступные расходы. Один запуск не доказывает универсальное превосходство или экономию подписочной квоты.

## 15. Порядок реализации и условия завершения

| Этап | Содержание | Условие перехода |
|---|---|---|
| G0 | Совместимость и карта реальных upstream-возможностей | Для каждой гарантии определён исполняемый механизм или явный блокер |
| A | Выбор моделей, раздельный бюджет, allow-shell, миграции | Нет скрытых моделей/прав/изменения активных grants |
| B | Independent-first shared review и сохранение blockers | Закрыты prompt/get/history/artifact/file обходы стадии |
| C | Read-only scout, конфигурационные snapshots, компактный контекст | Проверены отдельные истории, права и реальные роли/thinking |
| D | Sonic, managed helpers, accounting и остановка дерева | Пройдены отрицательные lifecycle/permissions/budget сценарии |
| E | Impact плана, явный перенос подтверждений, человеческий статус | Не потеряна безопасность при уменьшении ручной рутины |
| F | Полные регрессии, real-binary/live evidence, документы и выпуск | Все обязательные пункты пройдены либо выпуск явно ограничен по scope |

Разделить эти этапы на небольшие PR/коммиты. Не смешивать нестабильный helper-runtime с массовой переработкой планов без отдельной регрессии.

Готовый результат включает код, совместимые схемы хранения, тесты, документ совместимости, примеры настройки через MCP, справочник ошибок, безопасную миграцию и артефакты проверки. Старые инструкции, описывающие текущие режимы, обновляются только после прохождения соответствующих проверок.

## 16. Что не входит в задачу

Не входят новый OpenAI API-клиент, изменение пользовательской авторизации, покупка API-доступа, отдельный MCP-сервер на модель, захват открытых интерактивных чатов, переделка Channels/webhooks, облачная оркестрация, полная веб-панель, ОС-песочница и универсальный автоматический судья разногласий.

Не нужно переносить каждый read на маленькую модель или запрещать основной модели проверять критический код. Не нужно доказывать «любые две модели лучше одной» и заменять наблюдения рекламными обещаниями.
